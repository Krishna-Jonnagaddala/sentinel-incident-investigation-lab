# Sentinel Incident Investigation Lab

A self contained detection and response lab built on Microsoft Sentinel, plus a full
worked investigation of a simulated intrusion end to end: brute force against an
internet exposed RDP host, a successful logon with valid credentials, hands-on-keyboard
PowerShell, and outbound C2. The repo contains everything I used to build the lab, the
analytics rules that fired, the KQL I ran during triage, and the incident report I wrote
at the end.

The case study is written the way I'd hand it off in a real SOC. If you only read one
file, read [`investigation/case-INC-2024-0417.md`](investigation/case-INC-2024-0417.md).

---

## Why I built this

Most "SIEM projects" stop at deploying the tooling and screenshotting a dashboard. The
part that actually matters in a SOC is the investigation: taking a single alert and
working outward until you can say, with evidence, whether it's a real intrusion, how far
it got, and what to do about it. This lab exists to practice and document that loop.

Everything here is reproducible. The lab is two endpoints and a Sentinel workspace, the
"attacker" activity is generated by scripts in [`lab/attack-simulation/`](lab/attack-simulation),
and the detections are plain `.kql` files you can paste into Log Analytics.

## Lab environment

| Component | Detail |
|---|---|
| SIEM | Microsoft Sentinel on Log Analytics workspace `law-soc-lab` |
| Domain | `CORP` (single-domain, DC on `DC01`) |
| Windows endpoint | `FIN-WKS-04` - Windows 11, finance workstation, `10.10.20.45`, RDP exposed via NAT for the test |
| Linux endpoint | `WEB-SRV-02` - Ubuntu 22.04, nginx + OpenSSH, `10.10.20.60` |
| Domain controller | `DC01` - `10.10.20.10` |
| Windows telemetry | Windows Security auditing (4624/4625/4672/4688) + Sysmon (SwiftOnSecurity base config, tuned) forwarded via AMA |
| Linux telemetry | Syslog (`auth`/`authpriv`) via AMA |

Collection path: Azure Monitor Agent → Data Collection Rules → Log Analytics. Sysmon
events land in the `Event` table (`Source == "Microsoft-Windows-Sysmon"`); Security log
lands in `SecurityEvent`; Linux auth lands in `Syslog`.

Build notes and the exact DCR/audit-policy settings are in
[`docs/02-lab-setup.md`](docs/02-lab-setup.md). Network and data-flow diagram in
[`docs/01-lab-architecture.md`](docs/01-lab-architecture.md).

> Everything in this repo is simulated in an isolated lab. IPs, hostnames, and accounts
> are lab-controlled. The "malware" download and C2 beacon are harmless stand-ins
> (see [`lab/attack-simulation/README.md`](lab/attack-simulation/README.md)) chosen to
> generate the same telemetry a real intrusion would, without running anything malicious.

## The case, in brief

**Incident:** Sentinel INC-2417 / internal ticket **INC-2024-0417**
**Detected:** 2024-04-17 02:49 UTC
**Analyst:** K. Jonnagaddala (SOC)
**Rule that fired:** *Brute Force Followed by Successful Interactive Logon*
**Verdict:** **True positive.** Confirmed interactive compromise of `FIN-WKS-04` via the
`CORP\a.patel` account after a sustained RDP brute-force from `45.155.205.233`. Post-access
PowerShell pulled a second-stage script from `185.220.101.47` and established an HTTPS
beacon to `cdn-telemetry[.]net`. An SSH pivot toward `WEB-SRV-02` was attempted and
failed. Contained at 03:20 UTC (~31 min from detection).

### What happened, on a timeline (UTC)

| Time | Host | Evidence | What it means |
|---|---|---|---|
| 02:14:07 | FIN-WKS-04 | First `4625`, LogonType 10, src `45.155.205.233` | Brute force starts (RDP) |
| 02:14–02:48 | FIN-WKS-04 | 214× `4625` across `administrator`, `svc_backup`, `a.patel` | ~34 min password guessing |
| 02:49:11 | FIN-WKS-04 | `4624` LogonType 10, `CORP\a.patel`, same src IP | Attacker gets in with valid creds |
| 02:52:18 | FIN-WKS-04 | Sysmon `1`: `powershell.exe -nop -w hidden -enc …` (parent `explorer.exe`) | Hands-on-keyboard execution |
| 02:52:41 | FIN-WKS-04 | Sysmon `3`: powershell → `185.220.101.47:80` | Second-stage download |
| 02:52:55 | FIN-WKS-04 | Sysmon `11`: `…\Temp\update.ps1` written | Payload staged on disk |
| 02:53:20 | FIN-WKS-04 | Sysmon `22`: DNS `cdn-telemetry.net` | C2 domain resolution |
| 02:53:22+ | FIN-WKS-04 | Sysmon `3`: repeating → `185.220.101.47:443` ~60s | HTTPS C2 beacon |
| 03:05:44 | WEB-SRV-02 | Syslog: `Failed password` from `10.10.20.45` | SSH lateral-movement attempt (failed) |
| 03:20 | FIN-WKS-04 | Host isolated, account disabled | Containment |

Full evidence, every KQL query I ran, and my triage reasoning are in the

## How to reproduce

1. Stand up the workspace and endpoints per [`docs/02-lab-setup.md`](docs/02-lab-setup.md).
2. Deploy Sysmon with [`lab/sysmon/sysmon-config.xml`](lab/sysmon/sysmon-config.xml) and
   confirm events reach the `Event` table.
3. Import the four rules in [`detections/`](detections) as scheduled analytics rules.
4. Run the simulation scripts in order from a lab jump box. The
   *Brute Force Followed by Successful Interactive Logon* rule should raise an incident
   within one run interval.
5. Work the incident using [`investigation/hunting-queries.kql`](investigation/hunting-queries.kql)
   and compare your findings to the [case file](investigation/case-INC-2024-0417.md).
